# 网站开发约定

每个新网站在 `sites/<slug>/` 保存从需求到验收的交付物。实施 Issue 使用已经批准的固定版本作为输入；完成并审查通过的产物发布到根 `<slug>/`，与目录和汇总首页一并发布后验证线上结果。

## 一、生命周期

| 阶段 | 仓库与 GitHub 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 输入整理与入库 | 站点 README、PRD、可编辑设计源文件、预览及可信确认记录 | 交付物齐备，核对已有批准内容与入库内容一致；尚未确认的内容取得相应确认 |
| 输入版本固定 | 将已有确认记录与交付物版本、完整提交 SHA 关联 | 实施输入可追溯，无实质变化时沿用已有确认，不重复审批 |
| 拆票与分工 | 母 Issue、可独立验收的子 Issue、文件范围与依赖 | 每张实施票均有冻结输入、验收条件与明确边界 |
| 实现与验证 | 有效认领、任务分支、Draft PR、实际测试记录 | 当前变更满足 Issue 的验收条件，依赖满足交付规则 |
| 独立审查与验收 | 绑定当前 HEAD 的独立审查，验收结论和合并记录 | 当前版本满足协议、项目保护要求和具体批准范围 |
| 发布准备 | 根 `<slug>/` 产物、`site-catalog.json` 与根 `index.html` 的发布 PR | 每条新增入口都有真实且已验收的产物，公共改动有对应范围与审查 |
| 发布与收录 | 合并记录、Pages 运行、子站与首页的线上检查 | 部署成功，实际子路径及首页链接可用 |

需求和设计可以先在聊天或其他协作渠道中确认，再整理入库。确认来源可以是本次聊天、Issue、PR 或其他可信记录；在仓库入口或 Issue 中保留可核验的记录链接或摘录，并关联入库后的固定提交。只有尚未确认的内容，或影响实现、范围、验收的实质变更，才需要补充对应确认。

## 二、站点交付物

站点的 `slug` 使用稳定的小写连字符名称，确认后保留。新站采用下列目录；源码内部结构可按实际技术栈调整。

```text
sites/<slug>/
  README.md               站点入口、当前阶段、运行方式与交付链接
  docs/
    prd.md                 需求、范围、验收条件
    design/                可编辑设计源文件及评审预览
    acceptance.md          验收证据、当前结论与发布记录
  <工程文件与依赖锁文件>    实际使用的框架、源码和构建配置
```

- 复制 [PRD 模板](templates/site-prd.md)、[站点说明模板](templates/site-readme.md) 与[交付检查表](templates/site-delivery-checklist.md)后填写真实内容。尚未发生的审批、审查和发布保持未完成，不能照抄示例值。
- 可编辑源文件入库，并提供便于协作者评审的 PDF、图片或其他实际可读预览。PRD 写清页面、关键交互、异常与空态、内容依据和验收条件。
- 设计确认可以发生在入库前。核对可信确认记录所批准的内容与入库文件一致，记录确认人的可核验身份、批准范围及其对应的完整提交 SHA。已有确认且内容无实质变化时直接沿用；仅有“文件已上传”“设计已完成”的描述时，补齐实际确认依据。
- 拆票使用固定提交下的文件链接，例如 GitHub 的 `blob/<完整SHA>/sites/<slug>/docs/prd.md`。不要以会继续变化的分支链接作为唯一输入。
- 入库内容必须属于可公开交付的范围。构建排除只影响 Pages 输出，不影响公开仓库的文件可见性。

## 三、拆票与协作

每张实施 Issue 都应让新接手者知道要交付什么，以及怎样判断完成。

| 字段 | 填写要求 |
| --- | --- |
| 目标 | 可观察的用户结果或可验证的交付物 |
| 冻结输入 | 已批准的 PRD／设计文件、版本、完整提交 SHA 与批准记录 |
| 范围 | 精确文件或目录；写清不包含的页面、能力或公共资源 |
| 依赖 | 具体 Issue／PR；需要哪项输出后才能开始或交付 |
| 验收 | 可以实际核对的行为、内容、适配和验证证据 |
| 交接 | 已完成内容、剩余工作、已知限制及可继续的基线 |

- 同站并行前固定数据结构、接口与文件归属，使各子任务可以独立验证。发生范围重叠时先调整分工或完成交接，再写入共享文件。
- Agent 在实现前按日常 Skill 核对并发布有效认领；父任务内的本地子 Agent 使用父任务明确授予的子范围。独立写入 GitHub 的协作者按项目规则记录自己的身份和任务范围。
- `sites/<slug>/` 的实现、根 `<slug>/` 的发布产物、根导航和清单可以分别拆票。根 `index.html`、`site-catalog.json` 与 `_config.yml` 是跨站公共范围，不能由未认领该范围的站点任务顺手修改。
- worktree 可用于隔离并行任务，项目不要求特定客户端或模型。执行者仍需保留其他人的未提交工作与现有分支。
- 依赖未合并 PR 的任务按 Work-with-Agent 固定前置 HEAD 与净变更基线，保持 Draft；前置漂移后重新核对，不能把旧审查结论沿用到新版本。

## 四、构建与审查

- 站点 README 记录实际运行环境、安装、开发、构建、预览命令、输出目录和检查方式。使用依赖的工程提交实际锁文件，不强制所有站点采用同一框架。
- 本地预览使用真实的 `/static-pages/<slug>/` 子路径，检查图片、字体、CSS、JavaScript 与下载链接。存在前端路由时，验证刷新和深链访问，不假设静态主机提供服务器重写。
- 构建先输出到该站自己的构建目录，验证后再将产物复制到根 `<slug>/`。清理和复制的目标限定到已认领的站点路径。
- PR 记录本次对应的冻结输入、Issue、实际验证和剩余限制。实现者之外的审查者检查当前 HEAD 的完整变更、验收证据与依赖关系。
- 工程审查记录和协议批准按项目有效规则分别满足。合并所需的协议批准由另一位有效 Leader 职责身份或获授权的人类项目负责人提供，并满足现有 GitHub 原生保护要求。
- HEAD 或影响交付的前置版本变化后重新审查。只关闭实际完成且验收通过的 Issue；仍有范围未完成时保留明确的后续任务。

## 五、发布与首页收录

发布沿用 `main` 根目录的 Pages 配置。一次合并可能触发现有 Pages 构建，发布任务必须核对受影响范围和现有发布规则。

- 新站发布 PR 推荐同时交付根 `<slug>/` 的可用产物、`site-catalog.json` 条目与根 `index.html` 链接，并保留用于生成产物的源码提交、验证结果和回退范围。无需固定拆成两次发布；无法同批集成时，才先发布子站再补首页。
- 公共清单与首页由单独认领公共范围的集成任务负责，可以随站点发布 PR 一起交付。合并前检查每条新增入口都有真实、完整且已经验收的产物；仅有需求、设计或空目录的新站不进入清单。
- PR 中的新条目是本次待发布内容。合并后读取 Pages 实际部署结果，并验证子站 URL、关键资源和首页链接；只有这些检查通过后，才能在 Issue 或站点 README 中记录“已发布／已收录”。
- `site-catalog.json` 使用 `schema_version: 1`；`sites` 中每项保留 `slug`、`title`、`published_path`、`source_path`。`published_path` 为仓库根相对目录且以 `/` 结尾；`source_path` 指向真实源码目录，没有已迁入源码时为 `null`。
- 首页与清单当前由集成任务同步维护。合并前逐项核对真实 `index.html` 产物，发布后核对线上链接；不宣称存在自动收录流程。
- 更新旧站时保留原 URL，确认迁入源码对应的线上版本后再改产物。旧六站的 `source_path` 在迁入验收完成前保持 `null`。
- 发布前保存受影响目录的基线与摘要；发布失败时按 PR 中的回退范围处理，避免覆盖其他站点。改动 `_config.yml` 时验证旧站仍可发布，开发目录和协作资料不会进入 Pages 输出。
